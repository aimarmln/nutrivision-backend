# AGENTS.md

## Purpose

This document defines how coding agents should make changes in this backend repository safely and consistently.

Scope:

- Flask API backend only
- Code under `app/`, `migrations/`, and root runtime files
- No frontend/mobile/infrastructure guidance

## Project Architecture

Use the existing layered flow:

1. Route layer in `app/routes/`
2. Service layer in `app/services/`
3. Repository layer in `app/repositories/`
4. ORM models in `app/models/`
5. Validation schemas in `app/schemas/`

Request flow should remain:

- Route validates and parses input
- Service contains business logic
- Repository handles persistence
- Route returns standardized response helper output

Do not bypass services by putting business logic directly in routes.

## Runtime and Setup

Main runtime path:

- Entry point: `main.py`
- App factory: `app/__init__.py`

Start app:

```bash
python main.py
```

Default dev runtime uses host `0.0.0.0`, port `8000`, and debug enabled.

## API Contract Rules

Always use shared response helpers in `app/utils/responses.py`.

Success responses must use `success_response(...)` with shape:

- `status`: `success`
- `message`: meaningful message
- `data`: payload (or null if no payload)
- optional `pagination`

Error responses must come from centralized handlers in `app/utils/errors.py` via `error_response(...)` with shape:

- `status`: `error`
- `message`: error description
- `data`: null

Prefer raising framework/domain exceptions in services and let app-level handlers map them.

## Validation and Request Handling

Validation conventions:

- Use Pydantic schemas from `app/schemas/` in routes
- Parse body via `request.get_json()` then validate with schema constructor
- For UUID path params, use `validate_uuid_params(...)` middleware pattern where applicable

For image/file upload endpoints:

- Reuse validation utilities from `app/utils/validation.py`
- Keep MIME/type checks strict
- Reject invalid files with proper HTTP errors

## Auth and Security Rules

Auth stack:

- JWT setup in `app/extensions.py` and `app/__init__.py`
- Use `@jwt_required()` for protected endpoints
- Use `@jwt_required(refresh=True)` only for refresh endpoints

Service rules:

- Passwords must be hashed with Werkzeug helpers (never store plaintext)
- Token generation should remain in auth service flow (`create_access_token`, `create_refresh_token`)
- Keep identity as user UUID string

Do not log secrets or raw tokens.

## Database and Repository Rules

SQLAlchemy and session rules:

- Keep DB access in repositories only
- Use `with SessionLocal() as session:` pattern
- Commit/refresh in repository save/update methods
- Keep soft-delete filtering behavior consistent (`is_deleted == False` where expected)

Model rules:

- Follow existing SQLAlchemy typing/conventions
- Keep enum usage aligned with constants and helper utilities

## Migration Rules (Alembic)

Use Alembic for schema changes only.

Common commands:

```bash
alembic revision --autogenerate -m "description"
alembic upgrade head
alembic downgrade -1
```

Guidelines:

- One logical schema change per migration when possible
- Review autogenerated migration carefully before applying
- Never edit old migration history unless explicitly required
- Keep `migrations/env.py` configuration compatible with current app model imports

## ML Integration Cautions

ML components are initialized via `app/extensions.py` and loaded from `app/ml/`.

Agent guidance:

- Avoid unnecessary model-loading changes
- Treat model files under `app/ml/models/` as heavyweight assets
- Keep API behavior stable even if ML inference fails; surface controlled errors

## How to Add or Change an Endpoint

Follow this order:

1. Add/update schema in `app/schemas/`
2. Add/update repository operations in `app/repositories/` (if persistence changes)
3. Add/update business logic in `app/services/`
4. Add/update route in `app/routes/`
5. Register/verify blueprint behavior if new route module is introduced
6. Add migration if model/schema changes require DB updates

Keep changes minimal and localized to the correct layer.

## Error Handling Policy

Centralized handlers live in `app/utils/errors.py` and are registered in `app/__init__.py`.

When introducing new error paths:

- Raise meaningful exceptions (`BadRequest`, `NotFound`, `Conflict`, `Unauthorized`, etc.)
- Reuse existing handler mapping pattern
- Keep client-facing messages clear and stable

## Verification Checklist for Agents

Before finishing a change, verify:

1. Layer boundaries are preserved (no business logic leakage into routes)
2. Response format still matches shared helper contract
3. Protected endpoints still enforce JWT requirements
4. DB changes include valid migration and upgrade path
5. Imports and app startup still work (`python main.py`)
6. Changed endpoints return expected HTTP status codes for success and failure cases

## High-Risk Areas

Extra caution is required in:

- `app/services/auth_service.py`
- `app/utils/errors.py`
- `app/extensions.py`
- `migrations/versions/`
- `app/ml/`

Prefer incremental changes with explicit reasoning in these areas.

## Non-Goals

Do not introduce in this repository without explicit request:

- Frontend/UI changes
- New infrastructure/deployment stack
- Broad refactors across all layers with no functional need
